# Product Requirements Document
## AI-Based Fake News Detection System - Truthlens

**Version:** 1.0  
**Status:** Draft  
**Stack:** Next.js · FastAPI · HuggingFace · PostgreSQL  

---

## 1. Overview

### 1.1 Problem Statement

Misinformation spreads faster than corrections. Users currently have no reliable, real-time tool to verify the authenticity of news they encounter online — especially on social media and messaging platforms. Existing fact-checkers are slow, manual, and non-explainable.

### 1.2 Product Vision

A fullstack web application that instantly analyzes any news article — by URL, pasted text, or screenshot — and returns an authenticity score, a verdict, and a human-readable explanation powered by NLP and machine learning.

### 1.3 Goals

- Detect fake, misleading, and biased news with a confidence score
- Explain *why* content is flagged — not just *that* it is
- Provide a polished, demo-ready UI suitable for a project competition
- Support multi-signal analysis: NLP + source credibility + fact verification

### 1.4 Non-Goals (v1.0)

- No DevOps / CI-CD pipeline (out of scope)
- No mobile app
- No real-time social media stream ingestion
- No user authentication or accounts

---

## 2. Users

### 2.1 Primary User

**Competition judges / evaluators** — technical and non-technical assessors who will interact with a live demo. They need to be impressed quickly: paste a URL, see a result in under 5 seconds, understand the verdict at a glance.

### 2.2 Secondary User

**General public / students** — people who want to verify news before sharing. They need a simple input → clear output flow with no jargon.

## 3. Features

### 3.1 Core Features (Must Have)

#### F-01 · Multi-mode input
Users can submit news via:
- Pasting a URL (auto-scraped with `newspaper3k`)
- Pasting raw article text
- Typing a claim or headline

**Acceptance criteria:**
- URL input extracts article title, body, and source domain automatically
- Text input accepts a minimum of 20 characters
- Input errors are shown inline with helpful messages

---

#### F-02 · Authenticity score + verdict
The system outputs a 0–100 authenticity score and one of three verdicts:

| Score range | Verdict | Color |
|---|---|---|
| 70–100 | Likely real | Green |
| 40–69 | Suspicious / unverified | Amber |
| 0–39 | Likely fake | Red |

**Acceptance criteria:**
- Score is computed from a weighted fusion of three sub-signals (see F-03)
- Verdict label and color are shown prominently on the results page
- Score is displayed as a visual gauge (arc/dial), not just a number

---

#### F-03 · Multi-signal analysis engine
Three parallel signals feed into the final score:

**Signal 1 — NLP text analysis (weight: 40%)**
- Sensationalist language detection (VADER sentiment polarity)
- Emotional bias score (subjectivity via TextBlob)
- Clickbait pattern matching (regex heuristics)

**Signal 2 — Source credibility (weight: 35%)**
- Domain trust lookup from a seeded database of 200+ news domains
- Author credibility flag if author is unknown or unverifiable
- HTTPS + domain age check

**Signal 3 — ML model classification (weight: 25%)**
- HuggingFace pre-trained fake news classifier (`hamzab/roberta-fake-news-classification`)
- Returns a `FAKE` / `REAL` probability

**Acceptance criteria:**
- Each signal score (0–100) is shown individually in the results sidebar
- Final score = `(NLP × 0.4) + (Source × 0.35) + (ML × 0.25)`
- Processing completes in under 8 seconds for a standard article

---

#### F-04 · Sentence-level highlighting
The article body is rendered with color-coded sentence highlights:

- Green background = verified / neutral sentence
- Amber background = uncertain / unverifiable claim
- Red background = flagged as likely false or highly sensational

Clicking a highlighted sentence shows a tooltip explaining why it was flagged.

**Acceptance criteria:**
- Article is split into sentences server-side using `nltk.sent_tokenize`
- Each sentence receives an individual risk score
- Highlighting renders correctly for articles up to 2,000 words

---

#### F-05 · AI explanation
A plain-English paragraph explaining the verdict, generated by an LLM (Claude API or OpenAI), e.g.:

> *"This article uses highly emotional language in 6 of 14 sentences. The source domain (dailybuzz.net) has a low credibility score and no editorial standards listed. No major outlets reported the central claim."*

**Acceptance criteria:**
- Explanation is 2–4 sentences
- References specific signals that influenced the verdict
- Shown below the score gauge on the results page

---

#### F-06 · Analysis history
A `/history` page showing the last 20 analyses stored in the database.

Each row shows: article title, verdict badge, score, source domain, timestamp.

**Acceptance criteria:**
- Data persists in PostgreSQL across sessions
- Clicking a row re-opens the full results for that analysis
- History page loads in under 2 seconds

---

### 3.2 Extended Features (Nice to Have)

#### F-07 · Debiased rewrite
A "Show neutral version" button that calls the LLM to rewrite the article in a factual, balanced tone. Displayed as a side-by-side diff with the original.

#### F-08 · Community voting
Thumbs up / thumbs down below each result. If 5+ users disagree with the AI verdict, show a "community disagrees" badge. Votes stored in DB.

#### F-09 · Misinformation heatmap
A `/dashboard` page showing a chart of fake news density by topic category (Politics, Health, Sports, Finance) across all stored analyses.

#### F-10 · Chrome extension
A browser extension that extracts article text from any active tab and displays the authenticity score as an overlay badge on the page.

## 4. Technical Architecture

### 4.1 Stack

| Layer | Technology |
|---|---|
| Frontend | Next.js 14 (App Router) + Tailwind CSS |
| Backend API | FastAPI (Python 3.11) |
| ML / NLP | HuggingFace Transformers, TextBlob, VADER, nltk |
| Article scraping | `newspaper3k` |
| Database | PostgreSQL (via SQLAlchemy ORM) |
| LLM (explanations) | Claude API / OpenAI API |
| Deployment | Vercel (frontend) + Railway (backend) |

### 4.2 API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/analyze` | Main analysis endpoint. Accepts `{ url?, text? }`. Returns full result object. |
| `GET` | `/api/history` | Returns last 20 analyses from DB |
| `GET` | `/api/analysis/:id` | Returns single analysis by ID |
| `POST` | `/api/vote` | Accepts `{ analysis_id, vote: "up" | "down" }` |

### 4.3 Data Model

```
Analysis {
  id            UUID        PK
  input_type    ENUM        'url' | 'text'
  raw_input     TEXT
  article_title TEXT
  article_body  TEXT
  source_domain TEXT
  
  score_final   INT         0–100
  score_nlp     INT         0–100
  score_source  INT         0–100
  score_model   INT         0–100
  
  verdict       ENUM        'real' | 'suspicious' | 'fake'
  explanation   TEXT
  sentences     JSONB       [{text, score, reason}]
  
  votes_up      INT         default 0
  votes_down    INT         default 0
  created_at    TIMESTAMP
}

Source {
  domain        TEXT        PK
  trust_score   INT         0–100
  category      TEXT
  last_updated  DATE
}
```

### 4.4 Processing Flow

```
User input (URL / text)
  → FastAPI /analyze
    → [parallel]
        → newspaper3k scrape (if URL)
        → VADER + TextBlob NLP scoring
        → Source DB lookup
        → HuggingFace model inference
    → Weighted score fusion
    → LLM explanation generation
    → Sentence-level scoring
    → Store to PostgreSQL
  → Return JSON response
→ Next.js renders results page
```

## 5. UI / UX Requirements

### 5.1 Pages

| Route | Description |
|---|---|
| `/` | Home — input form (URL / text toggle), recent analyses strip |
| `/results/:id` | Full results dashboard — score gauge, verdict, signal breakdown, highlighted article, AI explanation |
| `/history` | Table of past analyses with filters |
| `/dashboard` | (Nice to have) Heatmap and stats charts |

### 5.2 Results Page Layout

```
┌─ Topbar ─────────────────────────────────────────────────┐
│  Logo   [analyzed URL shown]              [Analyze again] │
├─ Sidebar (220px) ──┬─ Main content ───────────────────────┤
│                    │                                       │
│  Verdict badge     │  Score gauge (arc dial, 0–100)       │
│                    │  AI explanation paragraph             │
│  Signal scores:    │                                       │
│  · NLP      72     │  ── Article with sentence highlights ─│
│  · Source   45     │                                       │
│  · Model    68     │  [Sentence]  [Sentence flagged ⚠]    │
│                    │  [Sentence]  [Sentence flagged ✗]    │
│  Source info       │                                       │
│  Community votes   │  ── Claim breakdown table ───────────│
│                    │  Claim 1: unverified                  │
│  [Rewrite ↗]       │  Claim 2: verified                   │
└────────────────────┴───────────────────────────────────────┘
```

### 5.3 Design Principles

- Every result shows *why*, not just *what* — explainability is the core UX value
- No result is shown as 100% certain — always display as a probability
- Color coding: green / amber / red maps to real / suspicious / fake consistently across all components
- Mobile-responsive layout (single column below 768px)

## 7. Constraints & Known Limitations

- Model accuracy is not 100% — the system should always present scores as probabilities, not facts
- Source credibility database starts with ~200 seeded domains; unknown domains receive a neutral score of 50
- LLM explanation generation adds ~2–3 seconds of latency; can be streamed to reduce perceived wait time
- `newspaper3k` fails on paywalled or JavaScript-rendered sites — show a graceful error and allow text fallback
- The HuggingFace model is English-only in v1.0
